== Welcome to Module 3 - Creating your vault file and launching the container.

As you can imagine when building an environment such as RHIS, there are lots of secrets that need to be maintained that you do not want in your inventory.
Since you are running ansible, there are a wide variety of secrets management tools that you can use to ensure that your data is safe.
The simplest, especially if you are building an environment (almost) from scratch is to use Anisible's native vault capability. 
In a brownfield environment, you might make use of an existing facility.


=== Creating a Vault File

As part of the deployment creation process, automation ensures that there is a vault directory and a vault_SAMPLES directory.
If you examine the vault_SAMPLES directory you will find a README.md file and a rhis_builder_vault_SAMPLE.yml file.

Use the provisioner terminal window or the vscode terminal window to create your vault file.
Make a copy of the rhis_builder_vault_SAMPLE.yml file in the vault directory.

e.g. From the provisioner tab running as ansiblerunner.
[source,bash]
----
cd /home/ansiblerunner/rhis/rhis-builder-inventory/deployments/example.local/vault_SAMPLES
cp rhis_builder_vault_SAMPLE.yml ../vault/rhis_builder_vault.yml

# now change to the vault directory
cd /home/ansiblerunner/rhis/rhis-builder-inventory/deployments/example.local/vault 
----

This file will become your definitive vault file. 
This particular directory is never overwritten when you run inventory_update.sh
Vault files are usually specific to the deployment you are creating and typically reside with the rendered configuration.

Currently the vault file is not encrypted. 
This makes the file easier to edit in your VSCode environment. 

Use the provisioner tab.
You encrypt the file by running the following command:

[source,bash]
----
cd /home/ansiblerunner/rhis/rhis-builder-inventory/deployments/example.local/vault
ansible-vault encrypt rhis_builder_vault.yml
----

You will be prompted for a password and to verify the password. 
You are doing it now on the initial copy so you don't lose anything valuable if you get it wrong.
You can simply copy over it at this point.

If you look at the file in VSCode or in the terminal, you will see something like:

=== Editing the vault file

Again from the provisioner tab as ansiblerunner.
You should already be in the vault directory

e.g.
/home/ansiblerunner/rhis/rhis-builder-inventory/deployments/example.local/vault

You can edit the file at the commandline by using:

[source,bash]
----
ansible-vault edit rhis_builder_vault.yml
----

This will launch your default terminal based editor.
In your lab this should be vim.

OK time to edit some vault variables.

There is a lot to the vault file but the instructions will limit focus to the relevant variables for this lab.
The file has been designed for a production environment where every password or secret entry needs to have its own unique value.
For labs and POCs it can be difficult to absorb with all the other concepts that you are working with.
To make it easier to get started, the sample vault file declares defaults and references that value to propagate it other like variables in the file.


The first default you find is your provisioning user. 
Don't change this.

```
rhis_builder_default_user: "ansiblerunner"
```

Next the configuration starts using that default user:

```
# at line 28
default_environment_username_vault: "{{ rhis_builder_default_user }}"
default_environment_password_vault: "eyJhbGciOiJIUz" 
```

Change the default_environment_password_vault to **rhisfromscratch**.

The section in the file should look like this:

```
default_environment_username_vault: "{{ rhis_builder_default_user }}"
default_environment_password_vault: "rhisfromscratch" 
```

The default_admin_username_vault is set to **"admin"** at around line 34.
IdM, Satellite and AAP installers all expect an admin user by default.
For production environments, these are typically disabled or changed after deployment, but for now you will leave this as is.


Then next set of variables you need to review are below.
These values are used to connect your rhis servers to the CDN to get content.
You only need these for the so called "bootstrap" servers in the RHIS environment.
Once a satellite server is up, your environment gets all its content from Satellite.
You will not change the values in this lab because you are working with systems that are bootstrapped already.

```
# at line 61 or so..
default_org_number_vault: 1234567     # a number without quotes listed on the Activation Key page
default_activation_key_vault: "rhis-builder" 
```

Your instructor will provide you with a temporary number and activation key to use for this exercise.

The last section that you need to review for IdM starts at line 160.
This is the Identity Management section;

```
#####################################
# Phase 2 - rhis-builder-idm vault
#####################################

# for bootstrapping the base idm install system to redhat cdn
# use cdn_activation_key_vault

# Note the redhat.rhel_idm roles use a different naming standard

ipa_admin_principal_vault: "{{ default_admin_username_vault }}"                                    # notsecret
ipa_admin_password_vault: "{{ default_environment_password_vault }}"                               # notsecret
ipa_dm_password_vault: "{{ default_environment_password_vault }}"                                  # notsecret
ipa_default_user_password_vault: "{{ default_environment_password_vault }}"                        # notsecret
satellite_user_default_password_vault: "{{ default_environment_password_vault }}"                   # notsecret

# Service user for interacting with IdM
ipa_principal_username_vault: "{{ ipa_admin_principal_vault }}"
ipa_principal_password_vault: "{{ ipa_admin_password_vault }}"

# for creating kvm services
# kvm_ssl_rsa_key_pass_vault: "{{ default_environment_password_vault }}"
```
In production, this is where you would set unique values for identity management secrets.
You really don't have to change anything here for the lab. 


In IdM, an identity is called a principal. 
The admin principal is admin.
You will use the default environment passphrase for your lab. 

**ipa_dm_password_vault** is a CRITICAL password. 
This is the "Directory Manager" password and is essentially root for the IdM installation. 
This is one of the reasons this file should always be encrypted in a secure location with very limited access.
In production, you can even keep this in a separate vault file with highly restricted access.
You can deploy it from a secure location at run time and delete the vaulted file after completetion.

Ansible secrets are protect by 

**no_log: true**

within the code so that execution does not leak secrets in log files or ansible output.

ipa_default_user_password_vault is used as a convenience for users that you provision during configuration.

Notice that you have this configuration in the vault file:

```
ipa_principal_username_vault: "{{ ipa_admin_principal_vault }}"
ipa_principal_password_vault: "{{ ipa_admin_password_vault }}"
```
These lines never really change.
They exist to abstract the variability in some collection implementations away from the user. 
You only set ipa_admin_principal_vault and ipa_admin_password_vault, and any code implementation differences are handled for you.

There are many other variables in this file, however, as you are only deploying IdM in this lab, you will not set them or discuss them.

Save and encrypt your vault file.


=== Launching the container

The user ansiblerunner will perform all your work.
SSH keys have been created as part of the bootstrap process and copied to all the lab hosts.
This is done as a normal part of bootstrapping in an RHIS environment.
This is only necessary for the bootstrap hosts.

Part of the work that was done when you ran the inventory_update.sh help script was to create a helper script for launching your container.
This provides us with a short command versus typing out a long ansible-playbook or navigator command.
The script is named after your deployment.

You should be able to find it in the root of the project.
[source,bash]
----
ls example.local.25.sh
----

Execute the script.
[source,bash]
----
./example.local.25.sh
----
