== Welcome to Module 3 - Creating our vault file and launching the container.

As you can imagine when building an environment such as RHIS, there are lots of secrets that need to be maintained that we do not want in our inventory.
Since we are running ansible, there are a wide variety of secrets management tools that we can use to ensure that our data is safe.
The simplest, especially if we are building an enviroment (almost) from scratch is to use Anisible's native vault capability. 
In a brownfield environment we might make use of an existing facility.


=== Creating a Vault File

As part of the deployment creation process, we ensire that there is a vault directory and a vault_SAMPLES directory.
If you examine the vault_SAMPLES directory you will find a README.md file and a rhis_builder_vault_SAMPLE.yml file.

Use the provisioner terminal window or the vscode terminal window to create your vault file.
Make a copy of the rhis_builder_vault_SAMPLE.yml file in the vault directory.

```
cd /home/ansiblerunner/rhis/rhis-builder-inventory/deployments/example.local/vault_SAMPLES
cp rhis_builder_vault_SAMPLE.yml ../vault/rhis_builder_vault.yml
```

This file will become our definitive vault file. 
This particular directory is never overwritten when we run inventory_update.sh
Vault files are usually specific to the deployment you are creating and typically reside with the rendered configuration.


=== Editing the vault file

Currently the vault file is not encrypted. 
This makes the file easier to edit in our VSCode environment. 
You encrypt the file by running the following command:

```
ansible-vault encrypt rhis_builder_vault.yml
```

You will be prompted for a password and to verify the password. 
We are doing it now on the initial copy so we don't lose anything valuable if we get it wrong.
We can simply copy over it at this point.

There is a simple extension that you can add to your environment that will allow to encrypt and decrypt your vault file on demand with a mouse click.

ansible-vault-inline dhoeric

This extension allows you to create a vault variable file in a directory of your choice and then use the contained password to encrypt and decrypt your vault file.
If you want to use this extention, you can install it easily
Then you need to create a vault.txt file to store you vault password. 

```
mkdir ~/.ansible
# edit and add your password as the only line in the file
vim ~/.ansible/vault.txt
```

Enter your password in the file and save.

Now when you are on the VSCode pane, you can press Ctrl+Shift+P and type ansible..
You will see Encrypt/Decrypt with ansible-inline
Selecting it will toggle your encrypted file from encrypted to decrypted and back.
It will also start to stay in the top position so that you can just press Enter to execute.
This make life easier.

OK time to edit some vault variables.

There is a lot to the vault file but we will limit our focus for now.
The file has been designed for a production environment where every password or secret entry needs to have its own unique value.
For labs and POCs this can be difficult to absorb with all the other concepts that we are working with.
To make it easier to get started, we declare some defaults and then use that value to propagate to all the other like variables in the file.


The first default you find is our provisioning user. 
Don't change this.

```
rhis_builder_default_user: "ansiblerunner"
```

Next we start using that default user:

```
# at line 28
default_environment_username_vault: "{{ rhis_builder_default_user }}"
default_environment_password_vault: "eyJhbGciOiJIUz" 
```

Change the default_environment_password_vault to **rhisfromscratch**.
The section in the file should look like this:

```
default_environment_username_vault: "{{ rhis_builder_default_user }}"
default_environment_password_vault: "rhisfromscratch" 
```

The default_admin_username_vault is set to **"admin"** at around line 34.
IdM, Satellite and AAP installers all expect an admin user by default.
For production environments, these are typically disabled or changed after deploymentn, but for now we will leave this as is.


Then next setup of variables we need to look at are these:
These values are used to connect your rhis servers to the CDN to get content.
You only need these for the so called "bootstrap" servers in the RHIS environment.
Once a satellite server is up, your environment gets all its content from Satellite.


```
# at line 61 or so..
default_org_number_vault: 1234567     # a number without quotes listed on the Activation Key page
default_activation_key_vault: "rhis-builder" 
```

Your instructor will provide you with a temporary number and activation key to use for this exercise.

For this lab the last section that we need to update starts at line 160.
This is the Identity Management section;

```
#####################################
# Phase 2 - rhis-builder-idm vault
#####################################

# for bootstrapping the base idm install system to redhat cdn
# use cdn_activation_key_vault

# Note the redhat.rhel_idm roles use a different naming standard

ipa_admin_principal_vault: "{{ default_admin_username_vault }}"                                    # notsecret
ipa_admin_password_vault: "{{ default_environment_password_vault }}"                               # notsecret
ipa_dm_password_vault: "{{ default_environment_password_vault }}"                                  # notsecret
ipa_default_user_password_vault: "{{ default_environment_password_vault }}"                        # notsecret
satellite_user_default_password_vault: "{{ default_environment_password_vault }}"                   # notsecret

# Service user for interacting with IdM
ipa_principal_username_vault: "{{ ipa_admin_principal_vault }}"
ipa_principal_password_vault: "{{ ipa_admin_password_vault }}"

# for creating kvm services
# kvm_ssl_rsa_key_pass_vault: "{{ default_environment_password_vault }}"
```

We really don't have to change anything here for the lab. 
In production, this is where we would set unique values for identity management secrets.

In IdM, an identity is called a principal. 
The admin principal is admin.
We will use the default environment passphrase for our lab. 

**ipa_dm_password_vault** is a CRITICAL password. 
This is the "Directory Manager" password and is essentially root for the IdM installation. 
This is one of the reasons this file should always be encrypted in a secure location with very limited access.
In production, you can even keep this in a separate vault file with highly restricted access.
You can deploy it from a secure location at run time and delete the vaulted file after completetion.
Ansible secrets are protect by 

no_log: true 

within our code so that we do not leak secrets in log files or ansible output.

ipa_default_user_password_vault is used as a convienence for users we provision during configuration.

Notice that we have this:

```
ipa_principal_username_vault: "{{ ipa_admin_principal_vault }}"
ipa_principal_password_vault: "{{ ipa_admin_password_vault }}"
```
These lines never really change.
They exist to abstract the variability in some collection implementations away from the user. 
You only set ipa_admin_principal_vault and ipa_admin_password_vault, and any code implemenation differences are handled for you.

I know that there are many other variables in this file, however, as we are only deploying IdM in this lab, we will not set them or discuss them.

Save and encrypt your vault file.
