== Welcome to Module 2

=== Understanding rhis-builder-inventory and deployments

**The rhis-builder-inventory**

The rhis-builder-inventory repository in github defines the structure and default configuration for an RHIS environment.
We make a disconnected copy of this repository for managing your own environments.
The repository contains a reference architecture for an idealized deployment of a Red Hat Infrastructure.
You are free to modify this in any way that you please. 
The goal of the reference architecture is to show you how the products were intended to work together to manage your environment.
The repository contains only configuration data (as tempates) and a small set of ansible plays to manipulate the configuation templates.
All of the code that builds and configures your environment based on the data resides in the rhis-provisioner container.
The container reads the configuration and applies it to your lab environment.

**Deployments**

RHIS has the notion of Deployments.
A deployment defines the DNS domain and the Red Hat Enterprise Linux servers that will support it.
A deployment typically consists of the following RHEL servers:
  - an Identity Management server
  - a Satellite server
  - an Ansible Automation Platform server
In this lab we will only be creating the Identity Management server.

A deployment is identified at a high level by the **inventory_basevars** file.
This is a configuration definition file written in YAML that defines the high level template variables used to create a deployment.
The deployment itself is managed through the directories of configuration files under **inventory_templates**


=== Understanding RHIS inventory_basevars.yml file

To create a deployment, we first make a copy of the sample inventory_basevars.yml file.
The recommended practice is to name this after your DNS domain that you will be managing.

```
cp /rhis/rhis-builder-inventory/inventory_basevars.yml /rhis/rhis-builder-inventory/example.com_inventory_basevars.yml
```

We will examine the new example.com_inventory_basevars.yml file a section at a time.

Let's start. Most of these are self explanatory.

```
# GLOBAL VARIABLES THAT APPLY TO ALL HOSTS
basevars_global_domain_name: "savage.test"
basevars_delete_logs: false       # Set to true to wipe the logs directory on inventory_update

# Deployment relationship
# Set basevars_disconnected_domain: true for air-gapped/highside deployments
# Set basevars_upstream_connected_deployment to the list of connected domains that feed content here
# Set basevars_downstream_disconnected_deployment to the list of air-gapped domains this deployment feeds
basevars_disconnected_domain: false
# basevars_upstream_connected_deployment:
#   - ""
# basevars_downstream_disconnected_deployment:
#   - ""
```

basevars_global_domain_name sets the domain name for all systems within the deployment. 
You will see in the inventory that we define server roles by shortname. 
When we deploy, the standard is <shortname><#>.<basevars_global_domain_name>
e.g. idm1.example.com

Next, is

basevars_disconnected_domain: false

We always need to create a connected environment first.
We can reference an existing connected environment, however, it must have a properly configured satellite instance.

The next section is fairly straightforward as well.

```
default_network: "192.168.140.0"
default_network_prefix: "22"
default_network_mask: "255.255.252.0"

default_bond_network: "192.168.142.0"
default_bond_network_prefix: "22"
default_bond_network_mask: "255.255.252.0"

rhis_primary_city: "Greenville"
rhis_primary_state: "South Carolina"
rhis_timezone: "America/New_York"
rhis_locale: "en"

rhis_time_servers:
  - "0.rhel.pool.ntp.org"
  - "1.rhel.pool.ntp.org"
  - "2.rhel.pool.ntp.org"
  - "3.rhel.pool.ntp.org"
```

The default_network and related variables define the network that your core rhis systems will exist in. 
This is for your idm primary and replica systems, your satellite and ansible automation platform node.
For this environment you can ignore bonded networks - this is for deploying bonded systems from satellite.
The rhis_primary_city, state, timezone and locale are only used in deploying users accounts to ease deployment for a single location.
As we are deploying kerberos, rhis_time_servers defines the time servers necessary to keep IdM aligned.

**NOTE:** You can extend the basevars implementation to suite your own environment.
This is one of the reasons we are making a copy of the repo vs. cloning.

**ATTENTION:** In this implementation of RHIS, as upstream templates change, merging newer features with customized configuration is manual.
We are in the process of implementing a tailoring files solution so that you can isolate your changes and extensions.
This will eventually allow you to consume all upstream changes without impacting your customizations.

The next section is important for automating system deployment.

```
basevars_default_baremetal_boot_disk: "/dev/nvme0n1"
basevars_default_baremetal_root_disk: "/dev/nvme0n1"
basevars_default_virtual_boot_disk: "/dev/sda"
basevars_default_virtual_root_disk: "/dev/sda"
# basevars_default_virtual_boot_disk: "/dev/vda"   # e.g. for KVM deployments
# basevars_default_virtual_root_disk: "/dev/vda"

rhis_aap_release_version: "2.6"
rhis_satellite_release_version: "6.19"
rhis_satellite_os_major_version: "9"
```
These variables define the defaults for baremetal and virtual system builds for the bootdisk and rootdisk.
This make provisioning steup in Satellite easier.
Remember that you can always override these at buildtime/runtime.

The rhis_ variables set our default deployment versions.
These are what systems will get built for AAP and Satellite.
We use RHEL9 for everything by default as Satellite only supports deployment on RHEL9. 
When Satellite supports RHEL10, everything will move to RHEL10.

The last section we will discuss is the RHIS system counts:

```
rhis_system_count:
  satellite: 1
  capsule: 1
  idm: 2
  gitea: 0
  logserver: 0
  aapgateway: 0
  aapcontroller: 1
  aapedacontroller: 0
  aaphub: 0
  aapdatabase: 0
  aapexecution: 0
  aaphop: 0
  kvm_hypervisors: 0
  quadlet: 2
  quay: 0
  ```

This list defines the different RHIS system roles we can deploy.
This list is extensible.
The list defines the number of systems of each type you want to add to your deployment.
There are limits. 
The limits for each server type are listed in inventory_basevars_limits.yml.
Exceeding a limit will generate and error on inventory update.
The default counts for a test environment are presented above.
We will only be deploying an IdM primary and replica, so when we edit ours, all values will be zero except idm which will be 2.

=== Understanding RHIS inventory_templates

Examine the files under the inventory_templates directory.
Do not modify any of the files at this time.
You will see that the inventory_templates directory is layed out like a standard ansible inventory directory.
We have all the recommended directories that you would expect.
Under **inventory_templates/host_vars/idm** you will find all the files that we will copy to generate our idm deployment.
You can examine these now.

**These are the files that you will eventually edit.**

**We try to never edit the deployment files directly.**

We may do this to quickly test something while debugging, but we want to make sure that we edit our templates and regenerate the deployment.
The templates are our source of truth.
The deployment is always generated and meant to be overwritten.
